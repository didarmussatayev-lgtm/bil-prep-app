# Подготовка в БИЛ — собранный репозиторий (шаги 1, 3, 4, 5, 7)

Этот README описывает, как собран репозиторий, и список расхождений между
шагами, которые пришлось поправить при сборке. Он не отменяет README самих
шагов — `step3-auth-README.md` и `step5-README.md` по-прежнему верны для
своих частей, просто в нескольких местах их пришлось скорректировать под
реально пересекающийся код.

## Стек и структура — без изменений

Next.js 14 (App Router) + TypeScript, PostgreSQL + Prisma, своя авторизация
(bcrypt + сессии в БД), Railway. Структура папок — как в step5/step3.

## Что было сломано на стыках и как это исправлено

### 1. `getCurrentUser()` не существует
В шаге 7 `lib/admin.ts` вызывал несуществующий `getCurrentUser()`.
Переписано на `requireApiUser("admin")` из `@/lib/auth/guards` (шаг 3) —
`requireAdmin()` в `lib/admin.ts` теперь адаптер над ним с той же сигнатурой
(`{ user, error }`), поэтому все API-роуты админки остались нетронутыми.
Постраничный `src/app/admin/layout.tsx` тоже переписан — на `requireAdmin()`
+ `requireSession()` из шага 3 (это два разных «requireAdmin»: один для
страниц с редиректом, другой — адаптер для API; в API-роутах используется
только `@/lib/admin`).
Заодно: студенческие роуты админки (`students/route.ts`, `.../password/route.ts`,
`.../logout/route.ts`) переведены с `bcrypt`/самодельного `revoked: true` на
`hashPassword`/`revokeUserSessions` из шага 3 — так, как и описано в самом
step3-auth-README («шаг 7: `hashPassword(generateTempPassword())` +
`revokeUserSessions(id, "password_reset")»). Плюс логины при создании ученика
приводятся к нижнему регистру (тоже прямое указание того README).

### 2. Админка ждала схему из черновика, а не из шага 5
`Progress.status/score` и `Test`/`TestQuestion` в реальной модели не
существуют. Переписаны:
- `prisma/schema.prisma` — единая схема, собранная из `auth-models.prisma` +
  `student-models.prisma` (авторитетная версия `Progress`/`TaskResult`/
  `TestAttempt`) + нужные поля из `schema-additions.prisma` (`Subject.slug`,
  `order`, `Task.slug/number/order`). `Test`/`TestQuestion` не включены —
  они оставлены закомментированными в конце схемы с пояснением, что вернуть,
  если понадобится редактируемый список тестов.
- `/api/admin/students/[id]/progress` — считает прогресс по факту:
  `Progress.learnedAt` (тема изучена) + `TaskResult.correct` (решённые
  задачи закрепления) + `TestAttempt` (сборные/разделные/тематические
  попытки), без Test/TestQuestion. Страница `admin/students/[id]/page.tsx`
  переписана под новый ответ API.
- `src/lib/admin-stats.ts` — то же самое, для общей статистики. «Средний %
  по теме» в этой версии считается как доля учеников, решивших хотя бы одну
  задачу закрепления темы верно (потому что `TaskResult` хранит только
  булево «решена ли задача», а не процент за попытку, — в модели шага 5
  такого числа просто нет).
- `/api/admin/students` (список) — общий % ученика считается той же
  функцией `getOverallProgress()`, что видит сам ученик на своей главной, —
  а не отдельной (неверной) формулой.

### 3. Контент из seed не так, как его ждал парсер step5
`explanationContent` из шага 4 — это Markdown (`### заголовок`, `**жирный**`,
`:::figure {json}` отдельной строкой), а `parseExplanation()` в шаге 5 умела
разбирать только готовый `ExplanationBlock[]` или голый текст без разметки.
Дописан построчный разбор: `###` → `heading`, `:::figure {...}` → `figure`
(с вытаскиванием `caption` из JSON), пустая строка — граница абзаца, всё
остальное — `paragraph`. `RichText` дополнен инлайновым `**жирный**`
(остальное — дроби `{a/b}`, формулы — по-прежнему шаг 6, как и было
написано в комментарии компонента).

### 4. Ещё три несостыковки, которых не было в списке, но которые ломали контент
Нашлись при сверке фактического seed/admin-кода с тем, что читает шаг 5:

- **`options`**: и seed, и форма админки пишут `Task.options` как
  `string[]` (буква — это позиция в массиве), а `parseOptions()` в шаге 5
  принимала только `{key,text}[]`. Строки без объектов отфильтровывались
  в пустоту — варианты ответа теста были бы просто не видны. Добавлена
  поддержка `string[]` (с сохранением поддержки `{key,text}[]` для
  совместимости).
- **`imageParams` vs `imageParamsJson`**: шаг 5 читал поле `imageParams`,
  а seed/админка пишут `imageParamsJson`. Поле в схеме и во всех
  Prisma-запросах шага 5 переименовано на `imageParamsJson`.
- **Один рисунок vs массив**: в семенных данных у некоторых задач `figure`
  — массив (например, тема 1.2, задача №7 — сравнение двух фигур), а
  `parseFigure()`/`Figure`/`TaskContent` в шаге 5 понимали только один
  объект. Переписаны на `parseFigures(): FigureSpec[]` + рендер всех
  рисунков подряд (`TaskContent`, `TaskCard`, `TestRunner`, `TestResult`).
- **`Subject.slug` нигде не создавался**: seed апсертил предмет только по
  `name`, а `slug` (нужен для `/bil/:slug`) не задавался вообще. Добавлено
  `slug: "math"` при апсерте.
- **`purpose` в Task** — подтверждено: действительно нигде не читается на
  стороне ученика. В схему не включено; seed использует `purpose` только
  локально (для slug и отчёта), в саму `Task` эта колонка больше не пишется.
- **Задачи-заглушки (`figure.kind === "placeholder"`)** по докам должны
  быть скрыты от учеников, пока рисунок не сделан, — в шаге 5 этой
  фильтрации не было нигде. Добавлена: на странице закрепления темы, в
  пуле вопросов теста (`lib/student/tests.ts`) и в счётчиках прогресса
  (`lib/student/progress.ts`, `lib/admin-stats.ts`, `admin/.../progress`) —
  иначе «3 из 8» на странице закрепления считало бы и скрытые задачи тоже.

### 5. Мелочи сборки
- `prisma/seed/index.ts` — путь `import { ENTITIES } from "../../lib/content-schemas"`
  указывал в несуществующую `prisma/lib/...` (в этом репозитории схемы
  лежат в `src/lib/content-schemas.ts`). Поправлено на относительный путь.
- `content-schemas.ts` — `slug` у `subjects/sections/topics` в БД обязателен
  и уникален, а форма админки его не присылает. На создании (`POST`)
  подставляется случайный (`autoSlug`); на редактировании (`PUT`)
  отсутствующий `slug` просто не участвует в апдейте — старое значение не
  затирается (актуально в первую очередь для `Subject.slug`, на которое
  завязан URL `/bil/:slug`).
- `package.json` — добавлены `zod` (используется в `content-schemas.ts`,
  раньше не было в зависимостях) и `tsx` (step3-auth-README прямо просит
  `npm i -D tsx` — им теперь запускаются и `create-admin.ts`, и seed;
  `ts-node` убран). Добавлен `"prisma": {"seed": "tsx prisma/seed/index.ts"}`
  для `npx prisma db seed`.
- `.env.example` — убраны `SESSION_SECRET`/`SESSION_LIFETIME_HOURS`,
  оставшиеся от черновика и ничем не читаемые (TTL сессии — константа в
  `src/lib/auth/config.ts`, токен сессии не подписывается, а хранится в
  БД по SHA-256). Добавлена подсказка про `ADMIN_LOGIN`/`ADMIN_PASSWORD`
  для `create-admin.ts`.

## Что не проверено автоматически

Здесь нет доступа к npm-реестру (нет сети), поэтому `npm install` /
`next build` / `tsc --noEmit` не запускались — вся сверка сделана
построчным чтением кода на стыках импортов/экспортов и полей Prisma-схемы.
Перед деплоем стоит прогнать:

```bash
npm install
npx prisma generate
npx prisma migrate dev --name init
npx prisma db seed
npm run build
```

## Шаг 6 — сделано

- **Виджет ввода ответа** (`src/components/tasks/AnswerInput.tsx`) — форма полей зависит
  от `Task.answerType`: одно поле для `integer`/`decimal`, числитель/черта/знаменатель для
  `fraction`, плюс поле целой части для `mixed`. Голого текстового поля нет.
- **Автопроверка на сервере** — `POST /api/tasks/:id/check`
  (`src/app/api/tasks/[id]/check/route.ts`). Логика сравнения — портированный
  `src/lib/_future/answerCheck.ts` → `src/lib/student/answerCheck.ts` (сравнение как
  рациональных чисел `a/b === c/d ⇔ a·d === c·b`, десятичные — с допуском на погрешность,
  `allowUnreduced` — требовать ли уже сокращённую дробь). Эталон (`correctAnswerJson`)
  всегда только на сервере, клиенту возвращается `{ correct: boolean }`. Результат пишется
  в `TaskResult` (upsert: неверный ответ не затирает `correct: true`, поставленный раньше)
  и обновляет `Progress.lastAttemptAt` — по нему уже раньше считался прогресс и статистика
  админки, так что оба сразу подхватывают реальные решения, без дополнительных правок.
- **«Показать решение»** — отдельный `GET /api/tasks/:id/solution`, отдаёт `solutionText` +
  отформатированный эталонный ответ по запросу (не вместе с условием задачи).
- **Параметрические SVG** (`src/components/content/Figure.tsx`) вместо текстовой заглушки:
  `fraction_bar` (полосы), `circle` (секторы), `grid` (закрашенные клетки), `number_line`
  (числовой луч с метками, `at` — число или `[числитель,знаменатель]`), `table` (обычная
  HTML-таблица — векторизовать тут нечего). `placeholder` по-прежнему текстовая заглушка —
  это единственный kind, который и должен остаться заглушкой (рисунок ещё не готов).

Ещё не сделано: полноценный рендер дробей/формул в `RichText` (`{a/b}` сейчас остаётся
как есть — это KaTeX-часть шага 6, которую я сознательно отложил, см. комментарий в файле).
